# AList BitQiu Windows 协议版（amd64）

在 AList 的 BitQiu 存储中增加 Windows 客户端密码登录、设备短信验证和原文件下载。保留原网页驱动供选择。

## 基础版本

- 官方镜像：`xhofe/alist:latest`，本次核对为 v3.65.0，linux/amd64。
- 固定基础镜像摘要：`sha256:499313cdb00ec53f60d9f00167df4ea737ca7f94f0d822673330f55bff8c9bfc`。
- 对应源码：AlistGo/alist，`ea628f9a4fb2dcd1f400a4a3f91ccb59b3c1da69`。
- 前端：官方 3.65.0。
- 协议参考：用户提供的 Windows 客户端 4.1.0.1；本仓库不分发其 EXE/DLL。

## NAS 部署

先备份原有 AList 数据目录。使用 `compose.bitqiu.yml`，把数据挂载路径改成现有 AList 数据目录，并设置已经存在的 NAS 下载目录（绝对路径），然后运行：

```sh
export NAS_DOWNLOAD_DIR=/你的NAS路径/下载目录
docker compose -f compose.bitqiu.yml up -d
```

也可下载 GitHub Release 中的 `alist-bitqiu-linux-amd64-image.tar.gz` 导入：

```sh
gzip -dc alist-bitqiu-linux-amd64-image.tar.gz | docker load
docker compose -f compose.bitqiu.yml up -d
```

**v3.65.0-bitqiu.13 起必须绑定 `/downloads`：** 在极空间 Docker 创建/编辑容器时，保留原 `/opt/alist/data`，另选择实际 NAS 文件夹，以读写方式绑定到 `/downloads`。镜像声明该卷以便 Docker 界面显示；未显式选择的自动管理卷、未挂载、只读及下载用户不可写会在正常启动时以配置错误退出。不能只在容器里建同名目录。Docker 镜像无法替管理界面选择宿主机路径，因此 Compose 要求 `NAS_DOWNLOAD_DIR` 且禁止自动创建不存在的源目录；极空间界面需要手动选定。

启动检查通过 `/proc/self/mountinfo` 检查独立挂载，并识别标准 Docker 本地管理卷路径 `.../volumes/<名称>/_data`。特殊卷插件或宿主机路径恰好采用此结构时不能可靠区分，请使用普通 NAS 文件夹绑定挂载。检查不通过不启动 AList，不删除原数据；升级前先补齐挂载。

数据目录、端口和 PUID/PGID 规则与原镜像一致。镜像仅支持 x86_64/amd64 NAS。若 GHCR 包尚未设为 public，可在 GitHub 包设置修改可见性，或使用 Release 镜像文件导入。

## 登录与验证

1. 新增 `BitQiu` 存储，`login_mode` 选 `windows`，填写挂载路径、账号和原始密码。**新建时 `sms_code` 留空，`login_action` 保持 `none`，不需要提前提供验证码。** `client_platform` 留空自动生成，`client_channel` 默认 `pc`。
2. 保存后存储会先写入数据库，再启动 Driver 进行密码登录。若需要新设备验证，Driver 自动发送首条短信，保存正常完成；存储列表状态显示“等待完成登录验证 / 新设备短信已发送”。无需重复新建存储。
3. 收到短信后，**重新打开刚创建的存储编辑页**，加载服务端保存的设备标识和 `client_state`，填入 `sms_code` 并保存即可；`login_action` 保持 `none`，也兼容显式选择 `verify_sms`。
4. 成功后状态为工作中，自动读取根目录 ID。操作恢复 `none`，验证码会清空，临时凭据会删除，正式会话保存并在重启后复用。

首次短信只在 Driver 启动取得新设备验证会话后自动发送一次。重启、重复保存、短信接口失败或网络超时不会自动重发。未收到短信时，等待至少 60 秒，重新打开编辑页选择 `send_sms` 并保存，以手动重发。验证会话本地最多保留 15 分钟，服务端可能更早使其失效。验证码错误会保留待验证会话，允许重新填写。

更换账号、密码、设备标识或渠道会使旧登录状态失效。`reset_login` 清空会话重新登录。若 API 会话过期，文件读取最多重新登录一次；如果再触发设备验证，则提示待验证；重新加载该存储启动 Driver 后发送首条短信。

`client_state` 包含敏感会话凭据；不要贴到问题报告中。它与账号密码一样保存在 AList 存储数据库中。

## 功能范围

- Windows 模式：密码登录、新设备短信验证、列目录（原生 `sort` 游标分页）、原文件地址获取、AList HTTP/WebDAV 下载。
- 本次 Windows 模式不迁移上传、删除、改名、移动、复制和建目录，调用会返回“不支持”。避免将客户端 Token 误发到原网页写入接口。
- `login_mode=web` 保留上游原驱动及其写入操作，仍受原网页登录兼容性限制。
- Windows 应用身份与 TV 不同；不接受直接混用 TV Token。没有对服务端权限或会员限制做绕过。

## HTTP 423 排查

根目录能显示、强制刷新后失败，可能是之前显示了缓存，不能据此认定只有子目录出错。v3.65.0-bitqiu.3 会在错误中显示 `endpoint`、数字业务码 `code` 及响应类型 `response`，不显示响应正文或凭据。更新并保留现有数据目录后，强制刷新一次根目录，记录完整的新错误提示。`code=none` 表示未取得有效数字业务码；不能仅凭 HTTP 423 就判断账号过期或目录锁定。

只有 HTTP 401/403/423 携带已知会话失效业务码，文件读取才会重新登录一次；不会自动发送短信或无限重试。该适配与诊断尚未经过实际账号的 423 场景验收。


## 已登录请求对比诊断（v3.65.0-bitqiu.4）

当无凭据 wget 请求返回 200，而 Driver 的真实请求返回 423 时，不再继续无凭据探测：

1. 更新镜像并重新创建容器，保留原数据目录。
2. 在 AList 管理后台重新打开已有 BitQiu 存储，将 `login_action` 选择为 `diagnose_http`，验证码留空，保存。
3. 保存时会提示“BitQiu 诊断完成”，存储状态会显示 `Go[...]；wget[...]`，把这段脱敏结果用于排查。这个提示用于展示诊断结果，不代表已修复登录。
4. 操作会自动恢复 `none`；诊断后重新打开编辑页并保存，可以恢复常规加载。

两次请求使用完全相同的已保存 Token、设备标识、根目录和分页参数。诊断不执行密码登录、会话刷新或短信发送；只读取根目录第一页。缺少完整会话时直接提示并停止。wget 请求使用私有临时目录和权限为 0600 的文件传递表单，凭据不出现在命令行参数，诊断结束即删除临时文件；输出只包含数字状态、数字业务码、类型和长度，不包含响应正文或凭据。诊断结果在 AList 存储状态可查看，无需 SSH 或手动读取数据库。

10401 已在无凭据探测中实际返回“参数不合法”，因此 Windows 模式不再仅凭该业务码清空会话或重新登录。仍需实际诊断才能确定 423 原因；两种 HTTP 客户端的结果差异本身不证明是哪一项底层协议差异导致。


## 子目录 423（v3.65.0-bitqiu.5）

文件夹元数据同时出现多个 ID 时优先使用 `dirId/dir_id`，普通文件优先使用 `fileId/file_id`，再回退到通用 `resourceId/resource_id/id`。旧版优先通用 ID，可能在多 ID 记录中选到非目录 ID；是否命中实际账号需要诊断确认。

`diagnose_http` 现在先对比根目录，再对比根目录第一页中第一个文件夹，各用 Go 和 wget 读取一次。状态显示 `root{...}；child{id_source=...,legacy_id_diff=...;Go[...]；wget[...]}`。`id_source` 仅报告选用的字段名，`legacy_id_diff` 表示相对旧版选出的 ID 是否不同，不输出文件夹名称或 ID 值。根目录第一页没有文件夹时显示 `none_on_first_page`；根目录请求失败或元数据无法解析时跳过子目录并报告原因。不分页扫描、不尝试替换 Token、不重新登录或发短信。

更新并重新创建容器后，先以 `login_action=none` 保存已有存储并强制刷新根目录，清除旧目录对象缓存，再打开子文件夹。如果仍报错，重新打开存储编辑页，选择 `diagnose_http` 保存，反馈完整的 root/child 脱敏结果。此版本尚未使用真实账号验证子目录 423 的根因。


## 固定镜像版本

GitHub Actions 为 GHCR 和 Docker Hub 同时发布 `latest` 和 `sha-<Git Commit 前12位>` 标签。两个仓库、两个标签来自同一份构建镜像。`latest` 随新发布更新；需要固定版本时使用该次构建的 SHA 标签。

```sh
# GHCR
docker pull ghcr.io/fv4004/alist_bitqiu:sha-<提交号前12位>
# Docker Hub：替换为仓库 Secret DOCKERHUB_USERNAME 对应的用户名
docker pull <DockerHub用户名>/alist_bitqiu:sha-<提交号前12位>
```

在成功的 Actions 运行中查看 Commit，取前12位即可。此规则从本次工作流更新起生效，之前仅发布到 Docker Hub 的 latest 不会自动补出历史 SHA 标签。更换版本后仍需使用目标镜像重新创建容器，并保留原数据目录挂载。


## 分页阶段排查（v3.65.0-bitqiu.6）

当根目录和子目录第一页诊断均为 10200，但正常打开子目录仍报错时，需要继续检查翻页。分页大小（page_size）保持原值即可，默认 24。

正常列目录的错误现在包含失败页码和是否携带游标，如 `page=2,cursor_present=true`，不包含游标值。`diagnose_http` 扩展为根目录第一页加首个子目录最多三页，每页均用 Go 和 wget 提交相同参数。报告包含 `page1{...;entries=24;more=true;cursor_len=...}` 等段落。它与正常列目录共享下一页游标读取逻辑，不自行构造或替换游标。不进行账号重新登录或短信发送。遇到错误、目录结束或缺失/重复游标立即停止；三页后仍有数据时标记 `stop=diagnostic_limit`，不宣称已经完整读取目录。若根目录第一页没有文件夹则不执行子目录诊断。

本版增加分页定位能力，未凭第一页成功就认定所有目录请求正常，也尚未确认实际账号的分页 423 根因。


## 连续分页的节奏与空响应 423（v3.65.0-bitqiu.7）

实际反馈显示普通浏览在第 13 页收到空响应 HTTP 423，而逐页诊断的前三页正常。此现象需要检查连续请求频率，不能仅凭 423 就认定账号过期。

Windows 模式新增 `page_interval_ms`（毫秒，默认 1000），控制正常目录请求开始时间的最小间隔，跨页、跨目录生效；旧配置留空时也默认一秒。可以设为 0 禁用，合法范围 0–30000。分页大小保持原值 24。间隔会增加大目录首次加载时间，完整读取后仍使用 AList 缓存。

仅当目录 API 返回空响应 HTTP 423 且没有业务码时，原页原游标最多额外重试两次，默认退避 2 秒、4 秒。若 Retry-After 要求等待更久，在 30 秒以内遵守该时间；超过 30 秒则返回提示，避免提前重试。等待和重试都可取消。不因这种 423 清空会话、重新登录或发短信；不将前面成功的页作为完整目录返回。JSON 业务错误、非空响应 423 和其它 HTTP 错误不会进入此重试逻辑。已知会话过期的原有单次登录处理保留。

后台 diagnose_http 仍用原始请求作对比，不应用正常列表的退避重试，以免掩盖原始响应。此版本已在离线回归中验证第 13 页暂时失败后的完整恢复，以及持续失败时的重试上限，但仍需实际账号确认请求节奏调整能否消除 423。

## 完整目录和可视化 NAS 下载（v3.65.0-bitqiu.8）

修正网页“全部显示”模式下旧请求默认只取 50 项的问题，并兼容 BitQiu 的布尔、数字和字符串下一页标记。网页选择分页或加载更多时仍保留原分页行为。更新后请强制刷新网页，再刷新网盘目录以替换旧缓存。网盘“分页大小”决定远端请求批次，不是目录总数上限。

极空间无需 SSH：

1. 在极空间 Docker 界面编辑或重新创建 AList 容器，保留原来的 `/opt/alist/data` 数据挂载。
2. 添加**读写**文件夹挂载：用极空间的文件夹选择器选择保存位置，容器路径填写 `/downloads`。已有容器需要按极空间界面要求重新创建，使新挂载生效。
3. 用 AList 管理员账号登录，点击页面右下角 **NAS 下载**，或打开 `http://NAS地址:5244/@nas`（有网站路径前缀时加上该前缀）。首次点击**启用已挂载的目录**，会添加 `/NAS下载` 本地存储；已有本地存储也可选择。
4. 左侧逐级打开 BitQiu 目录，使用上一页、下一页选择文件。支持跨页勾选同一目录的项目；进入其他目录会清空选择。
5. 右侧逐级选择本地 NAS 子文件夹，可新建文件夹；点击**下载已选项目到 NAS**。
6. 下方查看复制任务的状态、进度和错误，支持取消与重试。文件由容器直接写到 NAS，关闭浏览器后任务继续；容器重建前请先等待任务完成。

该页面仅管理员可用，不会向浏览器返回 BitQiu 密码、Addition 或客户端会话。下载复用 AList 后台复制任务，文件夹递归展开为子任务；同名目标在提交前拒绝，请选择新的空目录。挂载需有写入权限，实际权限取决于容器运行用户和极空间共享文件夹权限。新启用的 `/NAS下载` 自动加上继承到子目录的随机元信息密码，管理员可直接访问，访客不能浏览；已有本地存储沿用原访问设置。实际 BitQiu 账号的下载权限仍由服务端决定。

页面浏览器回归：安装 Python Playwright 和 Chromium 后运行 `python scripts/test-nas-browser.py`，可用 `CHROMIUM_PATH` 指定浏览器；测试使用模拟接口，不需要网盘账号。

## 登录白屏修复（v3.65.0-bitqiu.9）

v3.65.0-bitqiu.8 的 NAS 导航同步脚本存在加载时序问题，某些缓存和网络时序下可能使登录页白屏并停在 Loading。v3.65.0-bitqiu.9 将该脚本改为异步加载，保留目录分页与 NAS 下载功能。更新容器后强制刷新网页；仍需保留原 `/opt/alist/data` 挂载。

开发验证：下载匹配的官方前端到 `public/dist`，安装 Python Playwright 和 Chromium 后运行 `python scripts/test-alist-login.py`；可通过 `CHROMIUM_PATH` 指定浏览器，`--demonstrate-regression` 可复现旧逻辑。CI 在构建镜像前执行这些登录页检查。

## NAS 下载入口跳转修复（v3.65.0-bitqiu.10）

修复点击右下角 NAS 下载按钮出现 `storage not found; rawPath: /@nas` 的问题；该路径是独立页面，无需添加同名存储。入口使用完整页面导航，避免 AList 前端路由将其当作网盘目录。更新后强制刷新网页。旧版临时可在浏览器地址栏直接输入完整的 `http://NAS地址:5244/@nas` 后回车；有网站路径前缀时一并保留。

## 排序、文件信息与任务历史（v3.65.0-bitqiu.11）

NAS 下载页默认按修改时间从新到旧排列，可切换从旧到新、名称或文件大小排序。后端对完整目录排序后再分页，因此跨页顺序一致。上排放排序和每页数量，下方文件列表用两行显示名称、大小及修改时间。

任务区分为“正在进行任务”和“历史任务”。正在进行任务显示进度、已读取字节和最近传输速度；速度由容器实际读取的文件字节计算，不依赖浏览器轮询估算。历史任务每页显示 20 项，记录正常结束、用户取消、超时、其他失败及结束时间，并保留可用的错误详情。结束原因随复制任务数据保存，跨重启保留取决于 AList 的任务持久化设置；旧任务无法补推未知的结束原因。


## 文件选择和下载控制（v3.65.0-bitqiu.12）

文件列表支持全选当前目录（包括未显示的分页）、取消全选和逐项勾选。选中部分时全选框显示半选；排序和翻页保留同目录的选择，进入其他目录清空。右侧显示已选项数和本次总大小；选择文件夹时递归统计内部文件，按源对象身份去重，不重复累加文件夹汇总大小。未知大小单独标注，不按 0 计入准确总量。可视化 NAS 子目录选择方式不变。

任务分为正在进行和历史，提供每项开始、暂停、取消，以及“全部”和“选中项批量”两组独立控制。全部暂停先暂停等待队列，再停止正在传输的任务，避免空出的名额启动其他下载。单项/选中项暂停仅适用于下载中任务。全部开始会启动可恢复的等待、暂停和失败任务；同一复制队列的并发数仍由 AList 设置控制。不适用状态会跳过，返回成功、失败、跳过数量；取消需要二次确认。

暂停保留隐藏的 `.文件名.alist-bitqiu-任务ID.part` 临时文件。开始任务时重新获取源地址，优先 HTTP Range 续传，并检查偏移、大小及可用的 ETag/Last-Modified。服务器忽略 Range、实体变化或无法安全续传时保留进度，显示需从头重下；只有单独确认后才清空该任务临时文件。取消会终止后端请求并删除该任务临时文件，不覆盖已有最终文件。断网、写入失败等记录为失败，可开始重试；超时单独标注。

### 数据兼容与更新

增强任务记录保存在现有数据库 `task_items` 表的独立 `bitqiu_nas_v1` 项，不增加表或配置，不存储密码、会话、Token 或签名下载地址。新任务状态独立于旧复制任务的可选持久化开关；刷新网页仍以后台状态为准。容器重启后，等待或进行中的增强任务恢复为已暂停，保留临时文件供手动开始；历史保留。继续挂载原 `/opt/alist/data` 和同一 NAS 下载目录，勿删除 `.part` 文件。

原有 API、普通复制任务及其持久化设置保持可用。升级前已经提交的旧式复制任务仍在原 AList 任务管理中查看与取消/重试；不会将旧任务自动转成增强任务或假定旧文件支持续传。建议先完成或取消旧任务后升级。增强页面显示本版及后续创建的任务。旧版回退时保留数据和临时文件；旧版无法控制增强任务，应先暂停增强任务再回退。

目录统计最多递归 128 层、200000 个源对象，单次最多选择 50000 项，超过时明确提示分批。远程目录统计需要等待 BitQiu 返回完整列表。任务记录损坏时仅停止增强任务写入以保护原记录，AList 主界面仍可启动；请保留数据库备份并检查容器日志。

需求对应、改动文件和测试覆盖见 [NAS 下载验收报告](docs/NAS_TASKS_TEST_REPORT.md)。


## NAS 并发限制（v3.65.0-bitqiu.13）

下载任务区增加“同时下载上限”，可选 1–5，默认 5，保存到现有数据库的 `task_items / bitqiu_nas_concurrency_v1` 项，刷新和重启仍保留。不增加数据库表或全局复制配置。实际并发为 NAS 上限和原 AList 复制队列可用名额中较小者，不影响普通复制任务的原有规则。

调低上限时，根据本进程中实际开始下载的先后顺序，优先暂停最晚开始的超出部分；保留临时文件与字节进度，不标记为取消。暂停退出前仍占名额，避免等待任务抢占。等待中的任务保持等待；提高上限后自动补入等待项，已经暂停的任务需手动开始。全部开始和批量开始也遵守同一上限，无法绕过最多 5 个的限制。并发设置对这个 AList 实例的全部 NAS 下载生效，不是每个浏览器各自 5 个。

竖屏适配本轮仅评估：[可行性报告](docs/NAS_PORTRAIT_ASSESSMENT.md)。现有窄屏单列样式保留，不实施手机布局改版。
